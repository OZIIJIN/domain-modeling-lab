# 중간 회고 — STEP 1~2

- 기록일: 2026-11-23
- 상태: **중간 회고** (STEP 3~6 후 업데이트)

## 놓친 사고방식

| 기존 사고 | 개선할 사고 | 실제 실수 |
|---|---|---|
| 저장할 정보를 먼저 나열 | 어떤 행동이 허용·금지되는지 먼저 분석 | 회의실 속성을 비즈니스 규칙이라고 답함 |
| 기능 존재만 확인 | 주체·시점·조건·실패 시 동작 확인 | 예약 변경 시점은 불명확 |
| 구현을 업무 의미로 정의 | 업무 정의 → 규칙 → 상태 → 저장 전략 | 예약 취소를 삭제로 정의 |
| 고유 속성으로 엔티티 판단 | 독립 식별·업무별 개별 처리·생명주기 검토 | 예약의 식별 근거가 추상적 |
| 익숙한 설계를 바로 적용 | 전제·미결정 사항 명시 | 사용자와 관리자 통합 근거는 잠정적 |

## 핵심 개념

- **Domain Glossary:** 업무 용어와 의미를 일관되게 정의한다.
- **Business Rule:** 동작이 허용·제한되는 조건. 데이터 요구사항과 구분한다.
- **Entity Identity:** 속성이 바뀌어도 업무적으로 같은 대상을 구별·추적할 수 있는 성질.
- **Entity Lifecycle:** 생성·변경·업무 종료는 DB 데이터 삭제와 다르다.
- **Invariant:** 유효한 도메인 상태에서 반드시 지킬 조건. 개별 엔티티 외의 범위에 적용될 수도 있다.
- **Role vs Identity:** 권한상의 역할과 사용자의 업무적 동일성은 다르다.
- **Domain Assumption:** 확인되지 않은 설계 전제를 사실처럼 확정하지 않는다.
- **Entity vs Value Object:** 식별·동일성이 핵심인지 값 자체가 의미를 가지는지 검토한다.
- **Domain Model vs ERD:** 업무 의미·행동과 데이터 관계 구조는 관련되지만 일치하지는 않는다.

## STEP 2 추가 회고 — 사용 제한과 Identity (2026-11-23)

### 새롭게 잘한 판단
- 기존 후보 목록에 없었던 **사용 제한**을 자발적으로 발견했다.
- 한 회의실에 제한이 여러 개 있을 수 있고 그중 하나만 해제할 업무 시나리오를 근거로 식별 필요성을 설명했다.
- 해제 후 보관/삭제 정책을 미결정으로 남겨 구현 방식을 단정하지 않았다.

### 추가로 드러난 약점
- **생명주기 존재 → 반드시 별도 엔티티**라는 추론은 충분하지 않다. 값 객체/소속 구성요소 대안도 검토한다.
- **속성 값이 같음 → 동일한 엔티티**라고 추론하면 안 된다. 시작 시각이 같아도 해제 후 다시 등록한 제한은 다른 건일 수 있다.
- '같은 사용 제한이므로 변경'처럼 결론을 근거로 재사용하는 **순환 논증**을 피한다.
- 사용 제한 시간 **수정**은 원본 요구사항에 확정된 기능이 아니며, 설정·해제만 명시되어 있다.

### 새로 학습한 개념
- **Identity vs Attributes:** 객체의 속성 값이 아니라 시간이 지나도 업무적으로 같은 대상으로 인정하는 기준을 찾아야 한다.
- **Entity vs Value Object:** 각각을 구별해 처리할 수 있다는 사실만으로 독립적인 엔티티여야 하는 것은 아니다.
- **업무 이벤트와 데이터 보관의 분리:** '해제'와 '삭제'는 별개의 정책이다.

### STEP 3에서 검토할 것
- 회의실·예약뿐 아니라 **사용 제한의 책임과 생명주기**도 비교한다.
- 제한 시간 변경 전후의 동일성 유지가 실제 업무에서 필요한지 확인한다.
- 해제·취소·삭제의 차이와 미결정 정책을 명시한다.
