# STEP 2 — 엔티티 후보 도출

- 날짜: 2026-11-23
- 평가: **통과**

## 1. 최초 답변 — 원문

**엔티티 후보**: 직원, 회의실, 예약, 관리자

### 회의실

- 서비스에서 사용자가 예약하는 주체이기 때문에 구분이 필요하기 때문에 독립적인 식별이 필요하다.
- 사용 가능 여부, 이름, 수용 인원, 위치, 이용 가능한 시설 정보가 존재해야 한다.
- 관리자가 회의실을 등록하는 순간 생성되고 관리자가 회의실을 삭제하는 순간 끝난다.
- 이 엔티티는 이 엔티티만의 생명 주기를 갖기 때문에 다른 엔티티의 단순 속성으로 표현하면 부족하다.

### 예약

- 구분해야하기 때문에 독립적인 식별이 필요하다.
- 예약자, 회의실, 사용 시작 시간, 사용 종료 시간
- 직원이 예약 등록한 순간 생성되고 취소한 순간 끝난다.
- 고유 속성을 지기 때문

## 2. 최초 답변에 대한 멘토 피드백

| 항목 | 평가 |
|---|---|
| 회의실 독립 식별 | 특정 회의실 식별 방향은 맞지만 구체적인 업무 근거 부족 |
| 회의실 정보 | 이름·수용 인원·위치·시설 정보 적절 |
| 회의실 생명주기 | 관리자가 삭제하면 끝난다고 단정하기 어려움. 미래·과거 예약 정책 미정 |
| 사용 가능 여부 | 시간대별 제한이 있어 Boolean 하나로 충분한지 재검토 |
| 예약 독립 식별 | '구분해야 한다'는 근거로 부족 |
| 예약 생명주기 | 취소 시 업무 효력 종료와 데이터 삭제 구분 필요 |
| 고유 속성 | 속성이 있다는 이유만으로 엔티티가 되는 것은 아님 |

## 3. 추가 질문 ① — 예약의 독립성

**상황:** 직원 A가 월요일과 화요일에 각각 예약. 월요일 예약만 취소하려고 함.

**사용자 답변 (원문)**
> 직원이 본인이 생성한 예약을 조회할 수 있기 때문에 독립적으로 관리해야 한다.

**멘토 피드백:** 조회 가능이라는 이유만으로 독립 엔티티가 되는 것은 아님. 각 예약에 대한 변경·취소와 처리 결과를 **다른 예약과 독립적으로 관리해야 한다는 점**이 핵심 근거.

## 4. 추가 질문 ② — 지점

**상황:** 관리자는 담당 지점의 회의실을 관리하고 직원은 근무 지점의 회의실을 조회.

**사용자 답변 (원문)**
> 지점, 지점별로 회의실과 관리자가 속하기 때문에

**멘토 피드백:** 지점은 회의실의 소속과 조회·관리 범위를 결정하는 업무적 개념으로 적절한 후보. 단 독립 식별할 근거를 더 확인해야 함.

## 5. 마지막 검증 — 직원과 관리자

**두 설계:** A: 직원·관리자 분리 / B: 사용자 + 역할.

**사용자 답변 (원문)**
> 선택: B
> 판단 근거: 관리자와 직원이 나뉘는 것은 오직 사용 가능 기능으로 나뉜다고 생각해서 사용자 엔티티로 관리하고 역할을 나눈다.

**멘토 피드백:** B는 타당한 잠정안이나 '권한만 다르다'는 가정은 확정되지 않음. 동일 계정 체계인지, 한 사람이 두 역할을 함께 가질 수 있는지, 역할 변경 시 계정은 유지되는지 확인 필요.

## 6. 잠정 후보 (확정 아님)

- 사용자 (직원/관리자 통합 잠정)
- 회의실
- 예약
- 지점

## 7. 최종 평가

| 구분 | 결과 |
|---|---|
| 잘 도출 | 주요 엔티티 후보, 추가 지점 발견 |
| 최초 누락 | 지점 |
| 근거 부족 | 구분 필요·고유 속성·조회 가능만으로 엔티티라고 판단 |

**핵심:** 엔티티의 식별 근거는 실제 업무에서 대상을 독립적으로 다뤄야 하는 이유로 설명한다.

## 8. 추가 발견 — '사용 제한' 엔티티 후보 (2026-11-23)

### 자발적으로 발견한 후보

**사용자 최초 제안 (원문)**

> 사용 제한도 엔티티로 관리되어야 한다고 생각이 들었어 왜냐면 사용제한도 어찌됐든 생명주기가 별도로 존재하는 거자나

**멘토 피드백**

사용 제한은 회의실 자체의 생명주기와 별개로 설정·해제할 수 있으므로 독립 엔티티 후보로 검토할 만하다. 그러나 별도의 생명주기가 있다는 사실만으로 엔티티 여부가 확정되지는 않는다. 독립 식별과 업무 책임, 값 객체로 표현할 대안도 확인해야 한다.

### 추가 검증 ① — 개별 사용 제한 식별

**상황**: 회의실 A에 10:00~11:00 프로젝터 점검과 14:00~16:00 냉방 시설 보수라는 두 사용 제한이 있다. 첫 번째 제한만 해제하려고 한다.

**사용자 답변 (원문)**

> 회의실의 단순한 속성으로 관리하기에는 특정 사용 제한 시간이 존재하고 이걸 관리해야 하기 때문에 그렇게 생각하긴 했는데 사용제한이 여러개 있을 수 있는데 여러 사용 제한 속에서 특정 사용 제한을 식별할 수 있어야 한다고 생각해

**멘토 피드백**

- 여러 사용 제한 중 특정 제한을 찾아 해제한다는 구체적인 업무적 근거를 도출했다.
- 그러나 개별 항목을 구별할 수 있어야 한다고 해서 반드시 별도 엔티티가 필요한 것은 아니다. 회의실의 시간 구간 값 목록처럼 표현하는 대안도 존재한다.
- 시간 구간 자체 외에 변경 전후에도 유지되는 업무적 동일성이 필요한지 검토해야 한다.

### 추가 검증 ② — 해제 후 보관과 삭제

**질문**: 제한 ①을 해제하면 즉시 삭제해야 할까, 해제 상태로 남겨 둘 수도 있을까?

**사용자 답변 (원문)**

> 근데 이거는 아직 미결정된 정책 아니야? 사용 제한이 가능하다고만 기획서에는 나와 있잖아

**멘토 피드백**

- 명시 사실: 관리자가 사용 제한을 **설정**하고 **해제**할 수 있다.
- 미결정 정책: 해제 기록을 계속 보관하는지, DB에서 삭제할지, 상태로 남길지.
- 업무적 해제와 물리적 삭제를 분리했다는 점은 개선된 판단.

### 최종 검증 — Identity와 Attributes

**상황**: 프로젝터 점검 사용 제한의 10:00~11:00을 10:00~12:00으로 변경하는 것으로 가정.

**선택 (원문)**: A — 기존 사용 제한의 시간 변경

**판단 근거 (원문)**

> 음 근데 사용 제한 시작 시간이 동일하기 때문에 변경으로 봐야 한다고 봐 왜냐ㅕㄴ 해당 사용 제한은 동일한데 시간 값만 변경된거기때문에..?

**멘토 피드백**

- A는 가능한 잠정 설계이지만 근거에 순환 논리가 있다. '동일한 제한이므로 변경'이라고 주장하려면 무엇이 동일성을 유지시키는지 설명해야 한다.
- 같은 회의실의 동일 시간대에 제한을 해제한 뒤 새로 등록하는 경우에도 별개의 업무적 사건일 수 있다.
- **Attributes(속성 값)**가 같거나 바뀌는 것과 **Identity(동일성)**는 다르다.
- 기획서에는 제한의 설정과 해제만 있고 **시간 수정 정책**은 확정되지 않았다.
